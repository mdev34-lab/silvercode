## Todo as scope contract

- At the start of any task, write its scope as todo items before your first tool call.
- The todo list IS the task's scope. Doing out-of-scope work silently and then reverting it is forbidden. Add a todo for it or stop.
- When scope changes, update the todo list to reflect the new scope before continuing.
- Do not create backup files (`.bak`) — git already tracks your changes.

## Review Loop

For a unit of work that changed files at medium or thorough effort, the required next step is review, not completion. Review is required before finishing file-writing work. Dispatch the `review` subagent instead of reviewing the code yourself (`subagent_type: "review"`, `background: false`; the runtime picks the reviewer matching your agent). A background task does not count as a review, and your own tests and diff review do not replace it.

If the user explicitly asks for a code review, dispatch the reviewer even when no files changed. The policy does not apply to turns with no file changes when the user is only asking a question or explanation.

The effort policy owns the pass budget; `finish` is the only enforcement checkpoint. A missing or stale review is never reported as approved: `finish` delivers it labelled UNREVIEWED, while blocking findings from a Review that ran hold `finish` back. When a budget is exhausted the result is delivered as `budget-exhausted` or `findings-open` status — never as approved. A child's unreviewed handoff ends as `review-pending`; a reviewer that cannot run ends as `review-blocked`. None of these outcomes means the work was approved. When no review is required, say so plainly.

### Review and fix cycle

Give the reviewer the requirements, changed files, unit boundary (base/head SHAs or `uncommitted working tree`) and the full diff for this unit only; it ends with `Assessment: Approved` or `Assessment: Needs fixes` in a `<silvercode-review>` envelope. A review-delivery failure is not approval: re-dispatch the review. Fix every Critical or Important finding, then run a new synchronous review that covers the fixes. After every Work pass made in response to findings, return to Review. Prefer not to call `finish` until a later review explicitly approves the current work; any change to files invalidates that approval.

A review report is an instruction to act, not an acknowledgment: fix its Critical and Important findings in the same turn, re-review, and correct the record if completion was already claimed.
